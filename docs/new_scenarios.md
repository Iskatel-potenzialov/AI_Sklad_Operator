# Новые сценарии: Проверка перед заказом и подтверждение заказа

## 📋 Сценарий B: Проверка перед заказом

### Описание
Проверяет условия договора поставщика перед заказом, анализируя файлы:
- `contract.txt` — условия договора (минимальная сумма, условия оплаты, сроки)
- `quality_notes.txt` — качество товаров и рейтинг поставщика
- `order_history.txt` — история заказов и задержек

### Примеры запросов
```
"Проверь условия заказа у supplier_002"
"Можно ли заказать у ОфисМастер?"
"Проанализируй поставщика supplier_003 перед заказом"
"Стоит ли заказывать у БумагаСервис?"
```

### Ожидаемый результат
LLM анализирует все данные и даёт рекомендацию:
- ✅ **МОЖНО ЗАКАЗЫВАТЬ** — если все условия выполнены
- ❌ **НЕ РЕКОМЕНДУЕТСЯ** — если есть проблемы
- ⚠️ **ТРЕБУЕТСЯ ДОПОЛНИТЕЛЬНАЯ ПРОВЕРКА** — если нужны уточнения

Пример ответа:
```
## Проверка условий заказа: ОфисМастер ЗАО (supplier_002)

### Условия договора
- Минимальная сумма заказа: 3 000 руб.
- Условия оплаты: 50% предоплата, 50% по факту
- Срок поставки: 5-7 рабочих дней

### Качество товаров
- Общая оценка: СРЕДНЕЕ (3/5)
- Брак: 3-5% (выше нормы)
- Клей-карандаш: ПЛОХОЕ качество

### История заказов
- Задержек: 12 из 38 заказов (31.6%)
- Среднее время задержки: 2-3 дня
- Последние 3 заказа: все с задержкой

### Рекомендация
❌ НЕ РЕКОМЕНДУЕТСЯ заказывать

Причины:
1. Высокий процент задержек (31.6%)
2. Качество клея неудовлетворительное
3. Поставщик не отвечает 59 дней

Альтернативы:
- КанцТорг ООО (рейтинг 4.8, без задержек)
- КанцелярияПлюс ИП (рейтинг 4.2)
```

## 📋 Сценарий C: Подтверждение заказа

### Описание
Формирует предложение заказа и ждёт подтверждения от пользователя. После подтверждения записывает заказ в лог `data/orders_log.jsonl`.

### Примеры запросов
```
"Закажи товары у supplier_001"
"Создай заказ для КанцТорг"
"Подтверди заказ у supplier_003"
```

### Ожидаемый результат

#### Шаг 1: Проверка условий
Сначала система проверяет условия договора (как в Сценарии B).

#### Шаг 2: Формирование предложения
Если условия позволяют, система формирует предложение заказа:
```
⚠️ Требуется подтверждение

Действие: Создание заказа
Поставщик: КанцТорг ООО (supplier_001)

Товары:
• Бумага офисная А4 — 10 пачек
• Ручки шариковые синие — 50 шт.
• Карандаши простые HB — 30 шт.

Описание: Заказ товаров у поставщика КанцТорг ООО

[✓ Подтвердить] [✗ Отклонить]
```

#### Шаг 3: Подтверждение пользователем
Пользователь нажимает "Подтвердить" или "Отклонить".

#### Шаг 4: Запись в лог
После подтверждения заказ записывается в `data/orders_log.jsonl`:
```json
{
  "timestamp": "2026-09-12T15:30:45.123456",
  "supplier_id": "supplier_001",
  "items": [
    {"item_id": "item_001", "quantity": 10},
    {"item_id": "item_011", "quantity": 50},
    {"item_id": "item_014", "quantity": 30}
  ],
  "status": "confirmed",
  "run_id": "abc123-def456-ghi789"
}
```

#### Шаг 5: Результат
```
✅ Заказ подтверждён и записан в лог.

Поставщик: supplier_001
Товары: 3 позиций
Время: 2026-09-12T15:30:45.123456
```

## 🔧 Техническая реализация

### Новые узлы LangGraph

1. **load_supplier_files** — загружает файлы поставщика из файловой системы
   - Читает `contract.txt`, `quality_notes.txt`, `order_history.txt`
   - Использует Filesystem MCP

2. **check_order_conditions** — LLM анализирует условия договора
   - Проверяет минимальную сумму заказа
   - Анализирует качество товаров
   - Проверяет историю задержек
   - Даёт рекомендацию

3. **confirm_order** — формирует предложение и ждёт подтверждения
   - Использует `interrupt_before` для HITL
   - После подтверждения записывает заказ в лог

4. **route_after_load** — маршрутизирует после загрузки данных
   - `inventory_analysis` → `find_problem_items`
   - `check_order_conditions` → `load_supplier_files`
   - `confirm_order` → `load_supplier_files`

5. **route_after_check** — маршрутизирует после проверки условий
   - `check_order_conditions` → `END`
   - `confirm_order` → `confirm_order`

### Обновлённый workflow

```
START
  ↓
parse_request (LLM-классификация)
  ↓
route_request (Python-маршрутизация)
  ├─→ answer_general → END
  └─→ load_items
        ↓
      route_after_load
        ├─→ find_problem_items → analyze_items → END
        └─→ load_supplier_files → check_order_conditions
              ↓
            route_after_check
              ├─→ END (если check_order_conditions)
              └─→ confirm_order → END (если confirm_order)
```

### HITL (Human-in-the-Loop)

Для `confirm_order` используется `interrupt_before`:
```python
return graph.compile(
    checkpointer=checkpointer,
    interrupt_before=["confirm_order"]
)
```

Это останавливает граф перед выполнением `confirm_order` и ждёт подтверждения от пользователя через API endpoint `/api/run/{run_id}/approve`.
