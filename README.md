# AI-оператор склада канцелярии

## Что делает приложение

Система принимает запросы на естественном языке и выполняет реальные операции: анализирует складские остатки, проверяет условия заказов у поставщиков, формирует заявки, изменяет данные в Excel, ищет по базе нормативных документов.

Примеры запросов и сценарии, которые они вызывают:

| Пример запроса | Что делает система |
|---|---|
| «Что ты умеешь?» | Отвечает описанием своих возможностей |
| «Какие товары надо заказать?» | Анализирует остатки, находит дефицит и проблемных поставщиков |
| «Можно ли заказать item_023 у supplier_005?» | Проверяет договор, качество поставщика, историю, сравнивает сумму с порогом |
| «Закажи у supplier_001 недостающие товары» | Формирует заказ, ждёт подтверждения, пишет в БД, шлёт в Telegram |
| «Поменяй минимальный остаток item_012 на 50» | Извлекает число, ждёт подтверждения, пишет в Excel |
| «Какие нормы хранения бумаги?» | RAG-агент ищет по нормативному документу с итеративным уточнением |

**Как течёт запрос по системе:**

1. Пользователь вводит текст на фронте. Фронт делает `POST /api/run` в Backend и открывает SSE-соединение на `GET /api/run/{run_id}/events`.
2. Backend запускает LangGraph-граф в фоне. Каждый узел эмитит события в SSE-канал: `node_started`, `assistant_message`, `action_pending` и т.д.
3. В зависимости от классификации запроса (см. ниже) граф идёт либо в ветку данных (MCP-сервер), либо в RAG-ветку (RAG-сервис → Qdrant), либо в ветку мутации (HITL).
4. Фронт слушает SSE, обновляет лог выполнения и показывает панель подтверждения, когда приходит `action_pending`.
5. При подтверждении фронт делает `POST /api/run/{run_id}/approve` — граф резюмится через `Command(resume=...)` и завершает операцию (пишет в БД + Telegram или в Excel).

## Как разбирается запрос: классификатор через tool calling

Первый узел графа — `parse_request` (разбор запроса). Он решает, **какой из сценариев имел в виду пользователь**, и извлекает параметры (ID товара, ID поставщика, число).

**Как это устроено:**

Узел делает **один вызов OpenAI с одной tool-схемой** — `PARSE_REQUEST_TOOL`. Это **не Function Calling для выполнения действий**, а **tool как структурированный формат ответа**. Модель возвращает не текст, а объект по схеме:

```
{
  "intent": "confirm_order | inventory_analysis | check_order_conditions | update_min_stock | search_knowledge | general_question",
  "target_item_id": "item_012" | null,
  "target_supplier_id": "supplier_001" | null,
  "new_min_stock": 50 | null,
  "requires_item_data": true/false,
  "requires_supplier_data": true/false
}
```

**Почему так, а не промптом с JSON-ответом:** модель гарантированно возвращает объект по схеме. Числовое поле `new_min_stock` приходит как `integer`, а не как `"50"`. Enum из шести значений отсекает мусорные intent'ы. На старых версиях с текстовым JSON-ответом модель иногда возвращала `"50"` в кавычках, оборачивала в ```json, добавляла комментарии — всё это ломалось при парсинге.

**Как модель различает похожие intent'ы:** в `description` enum'а прописаны примеры фраз. Например:

- `check_order_conditions` — «Проверь условия заказа у supplier_001», «Можно ли заказать item_002 у supplier_003?»
- `confirm_order` — «Закажи товары у supplier_001», «Размести заказ»
- `inventory_analysis` — «Какие товары надо заказать?», «Каких товаров не хватает?»

Разница между «Можно ли заказать?» (проверка) и «Закажи» (создание) — принципиальная, и она разводится **на уровне промпта классификатора**. Без явных примеров модель путает эти два сценария.

**Fallback:** если модель по какой-то причине не вызвала tool (бывает при геоблокировках, таймаутах, странных формулировках) — `parse_request` возвращает `intent=general_question`. Граф уходит в общий ответ, не падая.

**Что дальше:** узел-диспетчер `route_request` смотрит на `intent` и решает, куда идти по графу.

## Граф сценариев

```
START
  ↓
parse_request (разбор запроса + классификация)
  ↓
route_request (диспетчер по intent)
  ├─→ answer_general → END                              (общий вопрос)
  ├─→ search_knowledge → END                            (RAG-поиск)
  └─→ load_items (загрузка товаров и поставщиков через MCP)
        ↓
      route_after_load (маршрутизация по intent)
        ├─→ find_problem_items → analyze_items → END    (анализ склада)
        ├─→ load_supplier_files → check_order_conditions
        │     ↓
        │   route_after_check
        │     ├─→ END                                   (только проверка)
        │     └─→ confirm_order → END                   (HITL + БД + Telegram)
        └─→ prepare_update → execute_update → END       (HITL + Excel)
```

**Три точки ветвления в графе:**
- `route_request` — сразу после классификатора, до загрузки данных.
- `route_after_load` — после загрузки товаров/поставщиков, выбирает ветку бизнес-логики.
- `route_after_check` — после проверки условий, решает, надо ли переходить к оформлению заказа.

**Checkpointer:** `MemorySaver` в `workflow.py`. Нужен для HITL — когда граф останавливается на `interrupt()`, всё состояние сохраняется, чтобы потом резюмироваться через `Command(resume=...)`.

## MCP: локальный сервер + HTTP-клиент

MCP применён **на двух уровнях**:

**1. MCP-сервер (`backend/mcp_server/server.py`, порт 8001)** — FastAPI-приложение, которое отдаёт четыре tool'а:
- `get_items(item_id?, category?)` — список товаров или один товар
- `get_item(item_id)` — конкретный товар
- `get_suppliers()` — список поставщиков
- `update_min_stock(item_id, new_min_stock)` — изменение минимального остатка в Excel

Транспорт — **`streamable-http`** (официальный HTTP-транспорт MCP SDK от Anthropic). Альтернативы были: stdio (процесс-в-процессе) и SSE (устаревший). HTTP выбран, потому что:
- сервер и клиент живут в разных процессах (микросервисная архитектура);
- клиент и сервер независимо перезапускаются;
- один MCP-сервер может обслуживать несколько клиентов (например, тесты + основной backend).

**2. MCP-клиент (`backend/mcp_client/client.py`)** — обёртка над MCP SDK, которая **из синхронных узлов LangGraph** обращается к HTTP-серверу. Под капотом:
- каждый вызов tool'а — это `async with Client(url) as c: await c.call_tool(...)`;
- поскольку узлы графа синхронные (`load_items`, `check_order_conditions`), клиент использует `concurrent.futures.ThreadPoolExecutor` для запуска корутины в отдельном потоке. `asyncio.run` тут не подходит — если event loop уже работает, он упадёт.

**Кто вызывает MCP:**
- `load_items` — товары и поставщики (для ветки анализа склада и заказов).
- `execute_update` — собственно запись нового `min_stock` в Excel (только после HITL-подтверждения).

**Кто не вызывает:** `parse_request`, `answer_general`, `search_knowledge` — они не работают с Excel.

**Почему MCP, а не просто openpyxl в backend:** изоляция данных от логики. Один сервис отвечает за Excel (чтение, запись, валидация схемы), другой — за оркестрацию LLM. Если завтра Excel заменится на 1С или PostgreSQL — меняется только MCP-сервер, backend не трогается. Плюс MCP-сервер соответствует официальному протоколу Anthropic — его можно подключить к любому MCP-совместимому клиенту (Claude Desktop, Cursor).

## RAG-агент: многозапросовый поиск со страховками

Ветка `search_knowledge` — **не линейный RAG** (1 поиск → 1 ответ), а **агент с циклом и тремя tool'ами**. Реализован в `backend/graph/nodes/search_knowledge.py`.

**Три tool'а, которые доступны LLM внутри узла:**

| Tool | Что делает |
|---|---|
| `search_documents(query)` | Эмбеддинг запроса через RAG-сервис → поиск в Qdrant → возврат топ-3 чанков выше порога 0.6 |
| `reformulate_and_search(query)` | Внутренний вызов LLM-переформулировщика → поиск по новой формулировке |
| `evaluate_relevance(question)` | LLM-судья проверяет, покрывает ли накопленный контекст аспекты вопроса |

**Цикл:** главный LLM-агент на каждой итерации решает — вызвать tool или сгенерировать финальный ответ. Максимум **5 итераций** (`MAX_ITERATIONS`).

**Типичный сценарий для составного вопроса** («Пожарная безопасность и ширина проездов?»):

```
Iter 1: search_documents('пожарная безопасность и ширина проездов') → 3 чанка
Iter 2: evaluate_relevance → {sufficient: false, missing: 'ширина проездов'}
Iter 3: reformulate_and_search → 'нормы ширины проездов для пожарной безопасности' → 5 чанков
Iter 4: evaluate_relevance → {sufficient: true}
Iter 5: финальный ответ
```

**Страховки от зацикливания:**

1. **Счётчик `consecutive_insufficient`.** Если `evaluate_relevance` дважды подряд вернул `sufficient: false` — цикл прерывается принудительно, генерируется fallback-ответ из накопленных чанков с пометкой «может быть неполным». Логика: если дважды искали и оба раза «мало», третий поиск ничего не изменит, только сожжёт токены.

2. **`MAX_ITERATIONS = 5`.** Жёсткий стоп, если счётчик не сработал (например, модель зовёт tools бесконечно).

3. **Дедупликация чанков по `chunk_id`.** Один и тот же чанк может попасть в топ при разных формулировках. Повторно в контекст не добавляется.

4. **Fallback-промпт.** Если цикл остановлен счётчиком или лимитом — финальная генерация идёт с другим system-промптом, который просит в начале ответа отметить возможную неполноту.

**Зачем счётчик — экономическая логика:**

На проблемных запросах (например, вопрос, где в базе нет ответа — «чертёжные инструменты») `evaluate_relevance` может возвращать `false` бесконечно: чанки находятся, но модель считает их неполными. Без счётчика — 5 итераций, из которых 3 последних бесполезны. Со счётчиком — цикл останавливается на 2 неудачах, экономия **~20–25% токенов** на таких запросах. На простых вопросах (когда `sufficient: true` на первой итерации) счётчик вообще не активируется.

**Как это видно в UI:** `tool_trace` узла прокидывается во фронт через SSE. В `ExecutionLog` видно каждое действие агента:

```
🔍 search_documents('ширина главного проезда') → 3 чанка
🧠 evaluate_relevance → недостаточно
✏️ reformulate_and_search → 'нормативы ширины проезда в закрытых складах' → 5 чанков
🧠 evaluate_relevance → достаточно
```

Это не «чёрный ящик» — видно, как агент планирует, оценивает, корректируется.

**Куда идёт RAG:**

Узел `search_knowledge` через HTTP обращается к **отдельно запущенному RAG-сервису** (`rag_service/server.py`, порт 8002) — `POST /embed`. Тот грузит `sentence-transformers` с моделью `sergeyzh/rubert-mini-sts` (dim=312) и возвращает вектор. Дальше backend стучится в Qdrant напрямую (`POST /collections/stationery_rag/points/query`).

**Почему RAG-сервис — отдельный микросервис, а не библиотека внутри backend:**

- **Torch + transformers — 500+ МБ зависимостей.** Backend работает на Python 3.13, RAG-сервис — на Python 3.11, потому что под 3.13 нет готовых колёс (wheels) для `torch` + `sentence-transformers` с `numpy<2`. Держать это в одном venv невозможно.
- **Модель грузится один раз при старте.** 130 МБ весов, загруженные в память процесса, переиспользуются для всех запросов. В backend’е пришлось бы грузить при каждом запросе или держать глобальный singleton (плохо для тестирования и reload’а).
- **Embeddings — общий ресурс.** Тот же сервис может использоваться в других сценариях (классификация intent'ов через векторную близость, дедупликация чанков).
- **Qdrant — серверный режим.** Запускается как отдельный процесс `.exe` (Rust) на порту 6333. Backend общается с ним по HTTP.

## HITL: подтверждение критичных действий

Применён в **двух узлах**:

| Узел | Что подтверждает |
|---|---|
| `confirm_order` | Заказ поставщику: список товаров, сумма, поставщик |
| `prepare_update` | Изменение `min_stock` в Excel: было → станет |

**Механика:**

1. Узел формирует proposal (dict с `action_type`, описанием, данными) и вызывает `interrupt({"pending_action": proposal})`.
2. LangGraph **останавливает** выполнение графа. Состояние сохраняется в `MemorySaver` (checkpointer) под `thread_id = run_id`.
3. В SSE отправляется событие `action_pending` с полем `action`. Фронт рендерит `<ActionApproval>` с кнопками «Подтвердить / Отклонить».
4. Пользователь жмёт кнопку → фронт делает `POST /api/run/{run_id}/approve` с `{"approved": true/false}`.
5. Backend вызывает `compiled_graph.ainvoke(Command(resume={"approved": ...}), config)` — граф **резюмится с той же точки**, где остановился. State восстановлен из checkpointer.
6. Узел получает результат `interrupt()` — это и есть `{"approved": true/false}`. Дальше исполняет соответствующую ветку: пишет в БД + Telegram или отменяет операцию.


**Почему HITL именно так:** LLM не выполняет необратимые операции молча. Заказ на 12 640 ₽, изменение данных в учётной системе — это действия с реальными последствиями, и они требуют явного подтверждения от пользователя. В нашем случае аудит — это запись заказа в SQLite с `run_id` в качестве ключа идемпотентности и уведомление в Telegram.

## SSE: события в реальном времени

**Endpoint:** `GET /api/run/{run_id}/events`.

**Как устроено:**
- `RunManager` держит по каждому `run_id` очередь событий (`asyncio.Queue`).
- SSE-генератор в `routes.py` читает очередь и отправляет события клиенту в формате `data: {...}\n\n`.
- Таймаут 120 секунд между событиями → отправляется `heartbeat`, чтобы прокси/браузер не закрыли соединение.
- Соединение завершается, когда приходит `run_finished` или `error`.

**Типы событий:**
- `run_started` / `run_finished` / `error` — жизненный цикл запуска
- `node_started` / `node_finished` — по одному на каждый узел графа
- `route_detected` — результат классификации (после `parse_request`)
- `assistant_message` — текст ответа LLM
- `tool_started` — действия RAG-агента (`tool_trace`)
- `retrieval_done` — найденные `chunk_id` и тексты чанков (для evals)
- `action_pending` / `action_resolved` / `waiting_approval` — HITL
- `heartbeat` — keep-alive

**Почему SSE, а не WebSocket:** канал односторонний (сервер → клиент), обратная связь идёт через отдельный POST-запрос на `/approve`. SSE проще в реализации (обычный HTTP), у браузера есть встроенный EventSource с автоматическим reconnect. WebSocket здесь не даёт ничего сверху.

## Evals: измерение качества

Инфраструктура оценки качества в `evals/`. Прогон устроен так: `run.py` берёт вопросы из `golden_set.jsonl`, отправляет их в backend по HTTP, слушает SSE, собирает результат, оценивает через три независимых слоя и сохраняет в `results.json` + БД (`eval_runs`).

### Golden set

`evals/golden_set.jsonl` — 6 эталонных кейсов. **Каждый кейс содержит:**

| Поле | Что это |
|---|---|
| `id` | Идентификатор (`rag_001` ... `rag_006`) |
| `query` | Текст запроса (что введёт пользователь) |
| `expected_intent` | Какой intent **должен** вернуть `parse_request` (эталон классификации) |
| `type` | Тип проверки: `llm_judge` — смысловая оценка через LLM |
| `expected_chunk_ids` | Список `chunk_id`, которые **должны** быть найдены retrieval'ом (эталон поиска) |
| `criteria` | Текст для LLM-судьи: что считать хорошим ответом, включая «НЕ должен» |

**Почему именно 6 кейсов и такие.** Каждый кейс проверяет свою грань системы:
- «Ширина проезда» — конкретный норматив (формула П=2В+900). Проверяет точность retrieval.
- «Бумага и картон» — многоаспектный вопрос (температура + влажность). Проверяет оба аспекта.
- «Клей» — специфический товар. Проверяет, что retrieval не путает категории.
- «Чертёжные инструменты» — вопрос, где в базе мало информации. Проверяет поведение при плохом retrieval.
- «Ручки и фломастеры» — правила с чёткими деталями (колпачком вниз нельзя).
- «Офисная бумага» — два числа в ответе (температура + влажность).

6 кейсов — это MVP для ловли регрессий в RAG-ветке. Планируется расширение до 30-50 (по всем 6 сценариям).

### Три уровня оценки

**Уровень 1 — Retrieval-метрики (детерминированные, без LLM).**

Считаются в `retrieval_metrics.py`. Берут список `chunk_id`, найденных агентом (из события `retrieval_done`), и список `expected_chunk_ids` из golden set. Сравнивают.

| Метрика | Формула | Что показывает |
|---|---|---|
| Precision@5 | релевантные в топ-5 / 5 | Доля мусора в контексте |
| Recall@5 | найденные эталонные / все эталонные | Потеряли ли нужное |
| Hit@5 | есть ли хоть один эталонный в топ-5 | Работает ли поиск вообще |
| MRR | 1 / позиция первого правильного | Насколько высоко правильный чанк |

Бесплатно (0 токенов), мгновенно, не зависит от LLM. Это «здоровье поиска» в чистом виде.

**Уровень 2 — LLM-судья (0-10).**

`judge_answer` в `judge.py`. Отдельный вызов `gpt-4o-mini` с temperature=0.1. На вход подаёт: вопрос, ответ системы, критерии из golden set. На выход — `{"score": 0-10, "reason": "..."}`.

Критерии пишутся руками под каждый кейс. Обязательно содержат:
- Что **должен** содержать ответ (например, «должен указывать диапазон +15 до +20 °C»).
- Что **НЕ должен** (например, «НЕ должен выдумывать конкретные цифры, которых нет в базе»).

Пункты «НЕ должен» — ключевой приём. Без них судья оценивает «нравится / не нравится». С ними — оценивает соответствие бизнес-требованию: если в ответе галлюцинация, score падает до 0-3.

**Почему отдельный вызов, а не тот же агент:** self-evaluation bias. Модель склонна хвалить свои же ответы. Отдельный вызов с другим промптом, другой temperature и без доступа к процессу генерации — судья не «оправдывает» решение агента, а оценивает результат как чёрный ящик.

**Уровень 3 — Faithfulness (0.0-1.0).**

`judge_faithfulness` в `judge.py`. Ещё один LLM-вызов. Разбивает ответ на отдельные утверждения и проверяет **каждое** — подтверждается ли оно найденными чанками.

Возвращает:
```json
{
  "faithfulness_score": 0.67,
  "claims": [
    {"claim": "хранят при 18-22°C", "supported": false, "reason": "в контексте 15-20°C"},
    {"claim": "влажность не более 70%", "supported": true},
    {"claim": "в заводской упаковке", "supported": true}
  ],
  "unsupported": [...]
}
```

**Зачем отдельно от судьи:** судья говорит «в целом ответ хороший». Faithfulness говорит «конкретно это утверждение — галлюцинация». Это разные вопросы. Ответ может быть оценён на 7/10 судьёй (в целом верный), но содержать одну выдуманную цифру. Faithfulness её поймает и покажет явно — в админке есть раскрывающийся блок «Показать выдуманные утверждения».

### Диагностическая матрица: три уровня работают вместе

| Симптом | Диагноз | Что чинить |
|---|---|---|
| Recall@5 низкий + score низкий | Retrieval провалился | Embeddings, база, query rewriting |
| Recall@5 высокий + score низкий | LLM галлюцинирует | Промпт финального ответа |
| Recall@5 высокий + Faithfulness низкий | Точечная галлюцинация | Anti-hallucination промпт |
| Precision@5 низкий при хорошем Recall | Мусор в контексте | Поднять threshold, уменьшить top_k |

Без матрицы видно только «5.33/10» — знаешь, что плохо, но не знаешь, **что** именно. С матрицей — точный диагноз.

### Учёт стоимости

Каждый LLM-вызов в backend копит стоимость под своим `run_id` — через `contextvars.ContextVar` и глобальный `_run_costs` в `utils.py`. В конце запуска `run_finished`-событие содержит `backend_cost` с `input_tokens`, `output_tokens`, `cost_usd`, `cost_rub`. Это позволяет в evals посчитать **полную стоимость прогона**: backend + судья + faithfulness. Один прогон 6 кейсов ≈ 0.79 ₽.

### Хранение результатов

Прогон сохраняется в SQLite в таблицу `eval_runs` (`backend/db.py`). Схема:
- `avg_score`, `passed`, `total_cases` — сводка качества
- `precision_5`, `recall_5`, `hit_5`, `mrr` — retrieval
- `faithfulness_avg`, `faithfulness_unsupported` — галлюцинации
- `backend_cost_rub`, `judge_cost_rub`, `faithfulness_cost_rub`, `total_cost_rub` — стоимость
- `duration_sec` — время
- `results_json` — все детали в JSON (полные ответы, chunk_ids, reasons)

Это позволяет сравнивать прогоны во времени, искать регрессии, строить графики.

## Детали по сценариям

### 1. general_question

Классификатор → `answer_general`. Один LLM-вызов с системным промптом «Ты AI-ассистент склада, вот что ты умеешь…». Данные не загружаются, MCP не вызывается. Дешёвый сценарий.

### 2. inventory_analysis

Классификатор → `load_items` → `route_after_load` → `find_problem_items` → `analyze_items`.

- `load_items` тянет все товары и поставщиков через MCP.
- `find_problem_items` **детерминированно** фильтрует: `quantity < min_stock` (дефицит), `last_ordered > 90 дней` (не заказывали), `supplier.last_contact > 30 дней` (поставщик не отвечает). Никакой LLM — чистый Python.
- `analyze_items` получает список проблемных товаров и через LLM генерирует анализ с рекомендациями и уровнями срочности.

Числа считает код, LLM только формулирует. Это anti-hallucination на уровне архитектуры.

### 3. check_order_conditions

Классификатор → `load_items` → `route_after_load` → `load_supplier_files` → `check_order_conditions`.

- `load_items` тянет товары + поставщиков.
- `load_supplier_files` читает три файла поставщика: `contract.txt`, `quality_notes.txt`, `order_history.txt`.
- `check_order_conditions` **сам считает числа**: сумму заказа (items_to_order × unit_price), минимальный порог из `contract.txt` (регуляркой), сравнивает. LLM получает уже готовые цифры и формулирует вывод — «можно заказывать» или «не рекомендуется».

Опять: математика — на Python, текст — на LLM.

### 4. confirm_order (HITL)

Классификатор → `load_items` → `route_after_load` → `load_supplier_files` → `check_order_conditions` → `route_after_check` → `confirm_order`.

- `load_items` для этого сценария строит `items_to_order`: все товары поставщика с `quantity < min_stock`, считает `total_cost`.
- `confirm_order` формирует proposal и вызывает `interrupt()`. Граф останавливается, состояние сохраняется.
- Пользователь жмёт «Подтвердить» → `_resume_workflow` → `Command(resume={"approved": true})`.
- После resume `confirm_order`:
  - Проверяет, был ли уже заказ с таким `run_id` (`UNIQUE` в таблице `orders`). Если да — идемпотентно выходит.
  - Пишет `order_data` в SQLite (`orders`).
  - Отправляет `send_telegram_message` через `backend/mcp/telegram.py` (httpx → Telegram Bot API).
  - Возвращает финальный `answer` со статусом.

`_resume_workflow` симметричен первому запуску — тоже через `astream`, чтобы фронт получал события по мере выполнения.

### 5. update_min_stock (HITL)

Классификатор → `load_items` → `route_after_load` → `prepare_update` → `execute_update`.

- Классификатор через Function Calling извлекает `new_min_stock` как `integer`.
- `load_items` грузит один товар по `target_item_id`.
- `prepare_update` формирует proposal `{old_value, new_value, product_name}`, вызывает `interrupt()`. Ждёт подтверждения.
- При «Подтвердить» → `execute_update` → MCP-клиент → `update_min_stock` tool на MCP-сервере → openpyxl записывает новое значение в Excel.

Реально меняются данные, не только читаются. Это единственный сценарий, где граф **пишет** в исходный Excel-файл.

### 6. search_knowledge (RAG-агент)

Классификатор → `search_knowledge` → END. Разобран выше — многозапросовый цикл с 3 tool'ами, счётчиком и fallback.

## Что ещё нужно понимать про систему

**Идемпотентность.** Таблица `orders` имеет `UNIQUE(run_id)`. Если пользователь дважды нажал «Подтвердить» в панели HITL — второй раз заказ не запишется, вернётся сообщение о дубликате. Это важно, потому что фронт может переоткрыть SSE после сетевой ошибки и повторно отправить `/approve`.

**Graceful degradation.** Если RAG-сервис или Qdrant упал — `search_knowledge` вернёт ответ типа «RAG-сервис недоступен: <ошибка>», но граф не упадёт целиком. Фронт получит `assistant_message` и `run_finished`. Аналогично с MCP — ошибка вернётся в `errors` state, но workflow завершится.

**Async везде, где возможно.** Узлы графа синхронные (по требованиям langgraph 0.2 для `interrupt`), но I/O внутри них асинхронный. MCP-клиент запускает корутины в отдельном потоке, чтобы не блокировать event loop uvicorn'а.

**Стоимость на каждый `run_id`.** Аккумулятор в `utils.py` копит `input_tokens`, `output_tokens`, `cost_usd`, `cost_rub`. Видно, сколько стоит один конкретный запрос от начала до конца. Это позволяет ответить бизнесу на вопрос «сколько стоит один заказ через AI».

## Как запустить

5 процессов, 5 терминалов:

```bash
# 1. Qdrant (:6333)
cd qdrant_server && ./qdrant.exe --config-path config.yaml

# 2. MCP Server (:8001)
cd mcp && ./backend/venv/Scripts/Activate.ps1
python -m backend.mcp_server.server

# 3. RAG Service (:8002)
cd mcp && ./rag_venv/Scripts/Activate.ps1
python -m uvicorn rag_service.server:app --port 8002

# 4. Backend (:8000)
cd mcp && ./backend/venv/Scripts/Activate.ps1
python -m uvicorn backend.main:app --port 8000 --reload

# 5. Frontend (:3000)
cd mcp && npm run dev
```

**Прогон evals:**

- Через UI: `/admin` → «▶ Запустить прогон evals». Опционально `--only rag_002,rag_004`.
- Через CLI: `./evals_venv/Scripts/Activate.ps1 && python evals/run.py`

Требует запущенных: Qdrant, RAG, Backend. MCP — только для сценариев `inventory_analysis` / `confirm_order` / `update_min_stock`.

## Что дальше (прод-роадмап)

- **PostgreSQL вместо SQLite** — многопользовательский режим, репликация.
- **Docker Compose / Kubernetes** — все 5 сервисов в контейнерах, единая команда запуска.
- **Очередь задач (Celery / RQ)** — вынести Telegram и отправку писем в фоновые воркеры.
- **Метрики (Prometheus / Grafana)** — latency, стоимость, error rate по каждому узлу.
- **Rate limiting** — защита от злоупотреблений OpenAI API (например, `slowapi`).
- **Roles & permissions** — viewer / operator / admin.
- **Реальная интеграция с поставщиками** — email или API вместо Telegram.
- **Расширение golden set** — с 6 RAG-кейсов до 30-50 по всем сценариям.
- **CI-прогон evals** — GitLab / Gitea CI или `pre-push` hook как regression test.
- **Prompt versioning** — сравнение v1/v2 промптов на одном golden set (A/B).
